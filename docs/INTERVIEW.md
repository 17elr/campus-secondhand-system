# 面试说明

## 可以准确描述的工作

将校园二手系统迁移到MySQL并完善Session认证、ID归属和意向交易事务；通过Spring Cloud Gateway MVC统一入口，OpenFeign对接独立通知服务，Outbox实现通知补投，Redis提供共享Session与公开商品详情缓存。保留Vue、Element Plus、13个原有分页列表及图片素材，使用原生Fetch处理会话和错误。

旧基线：d650859979324881753cf306c9c1cf2b8549de6c。2026-10-24是本轮个人改造时间，不能当作过去已上线时间。

## 为什么保留交易单体

商品预留、意向状态、快照和Outbox必须一起提交，放在同一MySQL事务内最容易验证。没有把商品和订单拆成两个服务，因此不需要分布式事务、Seata或远程持锁。这个项目展示的是三个Java进程的小规模服务实践。

## 为什么通知独立

通知在业务提交后可以延迟，通知进程宕机不应阻塞购买意向。它拥有独立表和故障边界，使用稳定事件ID幂等接收。只有站内通知，没有短信、邮件或WebSocket。

## Gateway为什么不能代替业务鉴权

网关主要统一路由和输入边界，market仍读取可信Session并查询当前数据库状态/角色。伪造身份请求头、修改localStorage或直接访问开发端口都不能授予权限。

## 为什么不用JWT

Redis Session满足共享会话、退出和强制失效需求。Session只保存用户ID、认证版本与CSRF令牌，角色来自数据库。保留轻量BCrypt组件，不声称实现完整Spring Security登录体系。

## 并发与重试怎么处理

统一用户→商品→订单加锁顺序；buyer_id+request_key唯一，同参数返回同结果，异参数409；活动商品生成列唯一索引兜底。取消必须匹配reserved_order_id，不能释放别人的预留或把已售商品上架。接口只记录线下意向，不涉及付款或退款。

## Feign为什么不放交易事务里

网络超时会延长行锁，且远端成功/本地回滚难以协调。先在本地提交Outbox，再用短租约认领后进行HTTP请求，交易无需等待通知。已完成的订单不会因为通知失败回滚。

## 为什么允许重复通知投递

远端提交成功后，本地确认前可能崩溃，所以无法靠HTTP返回实现恰好一次。事件ID保持不变，notice用唯一键和内容Hash去重，做到至少一次尝试、通知记录幂等。租约和重试状态保存在MySQL；达到3次失败后需管理员处理。

## 数据迁移如何避免误归属

昵称不是唯一身份。工具默认只审计，只有显式提供可证明的记录ID→账号ID映射才启用历史记录。冲突与不明确归属保留只读，不能删记录或默认归给管理员。已结束的H2 mem进程没有可恢复的持久数据；已知fixture演练不等于恢复真实用户历史。
